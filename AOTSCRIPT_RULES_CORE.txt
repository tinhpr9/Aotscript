- EXECUTION_ENV=TERMUX_ONLY.
- Codespaces KHÔNG sử dụng cho tới khi người dùng chủ động xác nhận hoạt động lại.

- GitHub connector/API chỉ READ-ONLY; không sửa/commit/push bằng connector/API.
- Mọi thay đổi repository chỉ được thực hiện trong Termux, bởi người dùng hoặc Codex đang làm trực tiếp trong workspace đã xác minh; không ghi repo qua GitHub connector/API.
- Codex được phép sửa file, chạy test/gate, commit và push trực tiếp trong Termux khi đúng phạm vi và tuân CORE + AGENTS; không yêu cầu người dùng thao tác tay nếu Codex có thể tự làm an toàn.

1. CHẤT LƯỢNG
- Ưu tiên: ĐÚNG → AN TOÀN → KỸ → GỌN → NHANH.
- “Làm nhanh” = làm thật kỹ và đúng, nhưng ít bước, ít rủi ro, tiện nhất.
- Không bỏ gate/xác minh/kiểm tra để tiết kiệm thời gian.
- Loại bước thừa, không loại bước cần thiết.
- Không để người dùng là người đầu tiên phát hiện lỗi có thể tự test trước.

1A. TỰ CHỦ CÓ ROLLBACK / GIẢM INTERRUPT
- Tự thực hiện đến cùng mọi thao tác thuộc đúng nhiệm vụ hiện tại nếu thay đổi đó có thể rollback an toàn, phạm vi được xác định rõ và có thể kiểm chứng trạng thái trước/sau.
- Nếu thử nghiệm, checker hoặc patch thất bại: tự rollback chỉ thay đổi do chính lượt làm việc tạo ra, phân tích nguyên nhân và tự sửa tiếp bằng phương pháp an toàn hơn; không bắt người dùng xử lý lỗi mà Codex có thể tự phục hồi.
- Không được phá trạng thái đã xác nhận tốt, không ghi đè/xóa/stage/rollback thay đổi ngoài phạm vi, không dùng git reset/force để tiện sửa.
- Không dừng chỉ để hỏi cho các bước đọc, chẩn đoán, gate, test, tạo temp hoặc thao tác reversible thông thường khi công cụ/sandbox đã cho phép tự chạy. Gom các kiểm tra READ-ONLY thành ít lượt nhất có thể.
- Chỉ ngắt để hỏi khi sandbox thực sự bắt buộc approval hoặc khi hành động có hậu quả khó rollback, đụng ngoài scope, liên quan secret, remote thay đổi/xung đột, runtime destructive, hoặc reasoning hiện tại chưa đủ để tiếp tục an toàn.
- Nguyên tắc "sai thì tự sửa tiếp" chỉ áp dụng trong phạm vi có rollback chắc chắn; không được dùng nó làm lý do bỏ preflight, backup, gate, postcondition, secret scan hoặc xác minh trạng thái thật.
- Có thể dùng/recommend approval dạng "don't ask again" CHỈ cho command/helper hẹp, đã kiểm chứng là READ-ONLY hoặc rollback-safe và bị giới hạn đúng phạm vi. Cấm persistent approval cho shell/interpreter hoặc prefix rộng như bash/sh/python/sed/git/curl/rm/su/pkill, cho commit/push, thao tác runtime destructive, secret, đường dẫn ngoài workspace đã xác minh hoặc Full Access.

1B. MỤC TIÊU SẢN PHẨM / TẬP TRUNG CHUYÊN MÔN
- Trước mọi phân tích kỹ thuật, phải xác định PRODUCT_GOAL và CURRENT_BLOCKER từ HANDOFF hiện tại; nếu HANDOFF đã nêu rõ thì không được biến một lỗi cục bộ, lỗi tool, lỗi sandbox hoặc lỗi setup thành mục tiêu chính.
- Mọi chẩn đoán/patch/test phải trả lời trực tiếp câu hỏi: thay đổi này giúp tiến gần mục tiêu sản phẩm hiện tại như thế nào.
- Khi task hiện tại là AOT Group Control, ưu tiên chuyên môn đúng miền: Android Activity/Task/foreground/resumed state; dumpsys activity/window/View Hierarchy; UI hierarchy/selector/coordinate mapping; timing/race; reference-follower action replication; relay/WebSocket/ACK/status; E2E và runtime lifecycle.
- Không lan sang tối ưu Codex, hook, setup, auth, Telegram, Worker hoặc hạ tầng khác trừ khi chúng thật sự chặn CURRENT_BLOCKER. Nếu phải xử lý blocker hạ tầng, sau khi blocker PASS phải quay lại ngay PRODUCT_GOAL đang dở.
- Không được kết luận từ triệu chứng. Phải dựng causal chain: observed symptom -> source state/event -> responsible component -> smallest validated fix.
- Khi có nhiều giả thuyết, ưu tiên phép đo có khả năng phân biệt chúng; tránh đọc/log/test rộng không làm tăng bằng chứng.
- Nếu HANDOFF thiếu PRODUCT_GOAL nhưng yêu cầu hiện tại của người dùng nêu rõ mục tiêu, dùng đúng mục tiêu đó và báo PRODUCT_GOAL_SOURCE=USER_REQUEST; không tự bịa mục tiêu khác. Nếu cả HANDOFF và yêu cầu hiện tại đều không đủ rõ để xác định sản phẩm/blocker thì DỪNG trước patch.

3. TRƯỚC PATCH TRÊN TERMUX
Phải xác định:
- REPO_ROOT thật;
- git remote get-url origin;
- git branch --show-current;
- git rev-parse HEAD;
- git fetch origin main;
- git rev-parse origin/main;
- git diff --name-only;
- git diff --cached --name-only;
- git ls-files --others --exclude-standard;
- git status --short --untracked-files=all.
Khi trạng thái cho phép:
- git pull --ff-only
- BASE_COMMIT="$(git rev-parse HEAD)"
Phải biết tracked/staged/untracked/deleted/renamed và đúng file mục tiêu.
Không dùng riêng git diff --name-only để kết luận sạch.
Nếu có thay đổi có sẵn ngoài phạm vi: dừng hoặc dùng workspace sạch riêng.
Cấm: ghi đè/stage/xóa/rollback thay đổi ngoài nhiệm vụ; git reset; force push; git add .

4. PATCH PHẢI DỰA TRÊN HEAD MỚI
- Tạo lại patch từ HEAD sau pull.
- Không tái dùng line number/whitespace/marker/str.replace/code cũ/giả định cấu trúc cũ.
- Có thể tái dùng phương pháp, nhưng phải nhận diện lại trên code hiện tại.
- Code khác dự kiến: dừng, đọc lại, tạo patch mới; không cố tìm marker gần giống.

5. XÁC ĐỊNH CẤU TRÚC
Python:
- Ưu tiên AST: FunctionDef/AsyncFunctionDef/Call và phạm vi class/method.
- Phân biệt definition/call/string/comment/docstring.
JavaScript:
- Xác định class/function/object/array thật.
- Lấy scope bằng parser hoặc cân bằng {}, [], ().
- Chỉ kiểm tra trong đúng scope.
Cấm text.count/source.count/global regex để xác nhận cấu trúc code.
MATCH_COUNT=1 chỉ được dùng khi trả lời được:
1) cấu trúc nào; 2) scope nào; 3) vì sao chính xác phải bằng 1.

6. CHECKER/POSTCONDITION CŨNG PHẢI TEST
- Không coi checker mặc nhiên đúng.
- Chạy thật logic scope/match/sinh nội dung/postcondition/rollback với input đại diện.
- Compile checker chưa đủ nếu có logic runtime.
- Checker crash => LỖI_BỘ_KIỂM_TRA; không quy lỗi repo; không chạy lại block lỗi.
Ưu tiên:
AST/parser/brace-balanced scope
> regex giới hạn scope
> exact text trong scope
> tuyệt đối không global text count.

7. PATCH TRÊN FILE TẠM
1) đọc file chính vào bộ nhớ;
2) tạo nội dung mới;
3) đúng một newline EOF;
4) ghi temp cùng filesystem;
5) syntax-check temp;
6) structure-check temp;
7) chạy chính postcondition trên temp;
8) PASS hết mới atomic replace/os.replace;
9) chạy lại gate trên file thật.
Temp fail => không thay file chính, không commit/push, báo lỗi đúng vị trí.

8. PYTHON SYNTAX
Không xuống dòng trực tiếp sau toán tử nếu biểu thức không nằm trong ngoặc hợp lệ.
Sai:
if len(text) >
    LIMIT:
Đúng:
if len(text) > LIMIT:
hoặc:
if (
    len(text)
    > LIMIT
):
SyntaxError phải báo file/line/column/source khi lấy được.
Không mặc định dòng 1. Không lấy được vị trí thì ghi:
Không xác định được vị trí lỗi để hiển thị ngữ cảnh.

9. SHELL / HEREDOC / MOBILE
- Không set -e hoặc set -Eeuo pipefail trực tiếp trong shell Termux hiện tại.
- Block dài chạy trong shell con; strict mode chỉ bật bên trong.
- Marker đóng heredoc: một dòng riêng, cột đầu, không ký tự thừa, khớp marker mở.
- Terminal chỉ hiện ">" => shell đang chờ hoàn tất/heredoc; script chưa chạy.
- Khi đó xác định marker cần đóng; không yêu cầu nhập secret/Device ID/URL.
- Không phụ thuộc Ctrl/Esc/Tab/mũi tên/history; lệnh phải dễ copy nguyên khối trên Android.
- Tránh heredoc lồng phức tạp.
- Command substitution có thể fail phải thu riêng output và exit status.

10. BACKUP / ROLLBACK
Trước sửa ghi:
BASE_COMMIT, local HEAD, origin/main, tracked/staged/untracked/deleted ban đầu, file mục tiêu.
Chỉ backup file mục tiêu.
Khi fail:
- chỉ khôi phục file do block hiện tại đổi;
- chỉ bỏ staging file của block hiện tại;
- không đụng thay đổi có sẵn/untracked có sẵn;
- không git reset; không commit; không push.
Chỉ báo rollback thành công sau khi đối chiếu trạng thái thực tế với ban đầu.

18. DIFF / STAGE / COMMIT / PUSH
Trước commit:
- đúng repo/branch;
- remote HEAD không đổi ngoài dự kiến;
- chỉ file mục tiêu;
- không tracked/staged/untracked/deleted/renamed ngoài scope;
- syntax/structure/JSON/EOF/diff-check PASS;
- diff không secret.
Hiển thị:
GIT_PAGER=cat git diff --stat
GIT_PAGER=cat git diff
Stage từng file cụ thể; không git add .
Sau commit: xác nhận commit mới thật sự tồn tại.
Ngay trước push: git fetch origin main và kiểm origin/main.
Remote đổi + đụng file/logic liên quan => đọc lại/áp lại trên HEAD mới.
Không force push.
Sau push:
git fetch origin main
LOCAL_SHA="$(git rev-parse HEAD)"
REMOTE_SHA="$(git rev-parse origin/main)"
Chỉ PUSH=THÀNH_CÔNG khi LOCAL_SHA == REMOTE_SHA và working tree sạch.

QUY TẮC CHỌN MODEL / REASONING

Trước mỗi nhiệm vụ code, phải tự đánh giá độ khó và dùng mức reasoning phù hợp.

- Low: việc rất đơn giản, đọc file, tìm chuỗi, sửa nhỏ rõ ràng.
- Medium: tác vụ code thông thường, ít file, logic không phức tạp.
- High: debug khó, nhiều file, race condition, async, state, parser, kiến trúc hoặc lỗi khó tái hiện.
- Extra high: vấn đề rất khó, nhiều nguyên nhân khả dĩ, thay đổi ảnh hưởng rộng hoặc cần suy luận sâu trước khi sửa.
- Max/Ultra: chỉ dùng khi High/Extra high chưa giải quyết được, vấn đề đặc biệt phức tạp hoặc sai sót có rủi ro lớn.

Không dùng Low chỉ để tiết kiệm quota nếu nhiệm vụ cần suy luận sâu.
Không dùng Max/Ultra cho việc đơn giản gây lãng phí quota.

Nếu mức reasoning hiện tại không đủ cho nhiệm vụ:
- DỪNG trước khi sửa;
- báo:
  CURRENT_REASONING=
  RECOMMENDED_REASONING=
  REASON=
- yêu cầu tôi đổi bằng /model rồi mới tiếp tục.

Với bug khó:
đọc code thật → xác định nguyên nhân → kiểm chứng giả thuyết → mới sửa.
Không tăng reasoning để thay thế việc đọc HEAD, kiểm tra code và chạy test.
